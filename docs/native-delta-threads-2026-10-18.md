# Native：DeltaNet逐次更新の工程別時間とhead並列方式の比較（#18、診断）

2026-10-18。計画と判定条件は[事前登録](native-delta-threads-plan-2026-10-18.md)にあり、計測後に変えていない。**ライブラリと既定経路は変えていない。** 測ったのは、診断用example（`forward_breakdown --delta`）の中だけである。

## 方法

- **測定機**：AMD Ryzen AI MAX+ 395（16コア32 thread）、Windows 11、AC電源、電源プランはバランス。
- **source**：`0fb99d4`（未commitの変更なし）。
- **driver**：`bench/delta_stage_profile.py`。
- **集計**：`bench/delta_stage_summary.py`。
- **計測の構成**：
  - 23 processを実行した。
    - 工程別：2 session × 5 thread数 × 2（短い入力／8192 tokens）。
    - 工程timerなし：5。
    - probe：1。
  - 方式は、repごとに先頭を入れ替えて同じprocessで交互に測った。
  - 比は、同じprocess・同じrepの対で求めた。対の数は、128〜874 tokensで6、8192 tokensで2。
- **数値**：すべてのforwardで、最終hiddenがライブラリのforwardとbit一致した。各入力のhidden SHA-256は、全thread数（1〜16）・全方式・両session・timerの有無を通じて1種類だった。

## 何が逐次更新の並列効率を下げていたか

前回の方式（`scoped`）で、16 thread・874 tokensの逐次更新の時間（合計0.272秒）を分けた。

| 原因 | 時間 | 割合 | 仮説 |
| --- | ---: | ---: | --- |
| 逐次の取り出し・準備・書き戻し | 0.12秒 | 45％ | H1 |
| threadの生成・join | 0.020秒 | 7％ | H2 |
| 本体 | 0.109秒 | 40％ | — |

- **H1（逐次の準備・書き戻し）**：主因だった。`fused`はこれを0.013秒（並列の書き戻しのみ）に減らした。
- **H2（threadの生成・join）**：thread数とともに増える。4 threadで6 ms、16 threadで20 msだった。rayon poolを使うと1〜2 msになる。gemm直後のworkerとの競合は、`pool`と`fused`では見えなかった。
- **H3（共有資源）**：本体が16 threadでも6.3倍（16 headなら理想16倍）にとどまる理由である。
  - 16 thread・874 tokensの`fused`では、全headの計算時間の合計（`busy_sum`）が1.47秒だった。逐次では0.66秒なので、同時に動かすと1 headが約2.2倍遅くなる。
  - probe（新しいn threadで別々のheadを同時に計算する）の結果：

    | 同時thread数 | 1 headの時間（874 tokens） | L2に収まる入力 | 同じコアを共有したthread | copy帯域 |
    | ---: | ---: | ---: | ---: | ---: |
    | 1 | 21.0 ms | 19.6 ms | 0 | 93 GB/s |
    | 4 | 26.7 ms | 21.9 ms | 0〜2 | 77 GB/s |
    | 8 | 34.1 ms | 31.7 ms | 4 | 75 GB/s |
    | 16 | 54.5 ms | 43.4 ms | 11〜13 | 94 GB/s |

  - L2に収まる入力でも同じように遅くなり、copy帯域も飽和していない。したがって、主因はメモリ帯域ではない。
  - 主因は、Windowsが16 threadのうち11〜14をSMTで同じコアに載せること（計測時の電源プランはバランス）と、全コア負荷時のclockである。
  - 同じコアへの配置を避けるにはaffinityの固定が要る。これは方針で採らない。したがって、この測定機では、16 threadでの本体の伸びはこのあたりが上限である。
- **headの偏り**：16 thread・874 tokensで14 ms（本体の13%）と小さい。
- **計時のコスト**：工程timerの有無による逐次更新の時間差は、`serial`で0〜3%、`fused`で−10〜+1%だった。いずれも別processどうしの差で、雑音と区別できない。結論は変わらない。

## E1の判定

| 条件 | 結果 |
| --- | --- |
| 1. bit一致（全forward、全thread・方式・sessionでhidden 1種類） | 満たす |
| 2. 4 thread以上の512／874 tokensで中央値0.95以下 | `fused`は0.843〜0.884で満たす（`pool`、`scoped`も満たす） |
| 3. 2 thread全入力と128 tokens全thread数で1.01以下 | `fused`は0.864〜0.947で満たす |
| 4. 8192 tokensの4 thread以上で、両sessionとも1.0以下 | `fused`は満たす。`pool`／`scoped`は計画上この入力を測っていないので判定できない |
| 5. 採用候補 | **`fused`** |

**結論：E1を満たす。** `fused`を候補に、ライブラリへの組み込み案を設計し、E2（公開API E2E）で採否を判定する。

- 1 threadでは、`fused`は0.99〜1.00だった。ライブラリの1 threadは計画どおり今の逐次loopのままにするので、この値は採否には使わない。
- 小さな入力のための閾値は設けない。128 tokens・2 threadでも短縮（0.947）があり、並列区間1回あたりの同期は約0.05 ms（16 thread・128 tokensで18区間合計1.4 ms）と小さいため。

## 16 threadで残る処理（`fused`、874 tokens、forward 3.397秒に対する割合）

| 処理 | 時間 | 割合 | 並列化 |
| --- | ---: | ---: | --- |
| 線形層の行列積 | 1.385秒 | 40.8％ | される。ただし16 threadで公式全体の約65％に当たる。#15と重なる |
| 要素ごとの演算（RMSNorm、q／kのL2、MLPのSiLU×up、逐次更新後のnorm、z gate、残差） | 0.78秒 | 23％ | 大半が1 thread |
| 計時の外の時間（大きなbufferの解放などと推定。未確認） | 0.36秒 | 10.5％ | — |
| 畳み込み＋SiLU | 0.300秒 | 8.8％ | されない |
| 重みの変換 | 0.096秒 | 2.8％ | されない |
| DeltaNet逐次更新（`fused`） | 0.12秒 | 3.6％ | される |

要素ごとの演算と畳み込みが理想的に並列化しても、forwardは約2.4秒で、公式の2.13秒には届かない。16 threadで公式並みにするには、行列積（#15）も必要である。

**次の候補の優先度**（見込み短縮量÷実装コスト）：

1. **畳み込み＋SiLU**
   - 見込み：最大約8%。
   - 実装：channel方向に独立で、1関数で済む。要素ごとの演算順序はそのままなので、bit一致が容易。
   - 次に試す価値が最も高い。
2. **計時の外の0.36秒**
   - まず中身を特定する。確保と解放のどちらか、計時の漏れか。
3. **RMSNorm／L2**
   - 見込み：数%。
   - 実装：Candleの総和順序を再現しないとbit一致が崩れる。リスクが高いので、後に回す。
4. **行列積**
   - #15の範囲。この作業では扱わない。
