# Native：ARM64で見つかった4つの差異の原因と対応（#18、PR #38）

2026-10-20。[host matrix](native-host-matrix-2026-10-19.md)のCIで、ARM64に次の4点が見つかった。原因・影響・対応を分けて記録する。対象はmain `95e122d`＋PR #38で、推論の既定経路（`src`の非試験コード）は変えていない。

1. query blockに分けたattentionが、1 blockの結果とbit一致しない。
2. debug buildが`gemm-f16` 0.19でcompileできない。
3. 3秒の期限に対して、`Model::decide`の停止に8.5〜8.9秒かかる。
4. gemmのCACHE_INFOが、CPU・OSによって違う。

## 方法

- **ARM64**：一時的なworkflow（`diag/arm64` branchの`arm64-diag.yml`）で、ubuntu-24.04-armとwindows-11-arm（どちらもCobalt 100、4 vCPU）を測った。
  - run 39321756989：attention、debug build、モデル、期限。
  - run 39325381427：CLIの強制停止。
- **x86_64の対照**：手元のi7-1360P（Windows）で同じ診断を実行した。
- **診断用example**：
  - [`attention_block_diff`](../runtime/rust/examples/attention_block_diff.rs)：
    - `synthetic`：library試験と同じデータで、attentionの3段階（scores、softmax、value積）を行ごとに比べる。あわせて、行列積の1行目を、m行の積の中で計算した場合と1行だけで計算した場合とで比べる。
    - `model`：forwardを、512行ずつのblockと1 blockで同じprocess内で実行し、hidden・確率・判定を比べる。
  - [`deadline_trace`](../runtime/rust/examples/deadline_trace.rs)：forwardの期限確認（`check`）が呼ばれた時刻をすべて記録する。
- **証跡**：[research/native-host-matrix-2026-10-19/](research/native-host-matrix-2026-10-19)の`arm64-diag-*`と`x86-diag-i7-1360p`。

## 1. attentionのblock化とbit一致

### 原因

**1行だけのblockが、gemmの別経路で計算されることにある。**

- gemm 0.19は、m≤1の積をgemv経路で計算する（`gemm-common/src/gemm.rs`の`gemm_basic_generic`）。それ以外は、microkernel経路で計算する。
- gemvはkの全体を1回で足す。microkernelは、kをkcで区切って部分和を足す。kcはCACHE_INFOから決まり、下限は512である（4.を参照）。
- **ARM64**：2経路で和の順序が違う。
  - 行列積の1行目を1行だけで計算すると、m＝2〜512のどの積の1行目ともbit一致しなかった（k、nは7〜1024の7通り）。
- **x86_64**：kc≧kなら、2経路はbit一致する。
  - i7-1360PのP-coreでは、同じsweepですべてbit一致した。
  - kc＜kになると、microkernelだけがkを区切るため一致しない（下の「x86_64でのk＞512」）。

### block化した場合の一致・不一致

| seq、block | blockの行数 | ARM64 | x86_64（i7-1360P、P-core） |
| --- | --- | --- | --- |
| 7、1／7、3 | 1×7／3＋3＋1 | 不一致 | 一致 |
| 8、3／9、3 | 3＋3＋2／3＋3＋3 | 一致 | 一致 |
| 9、8／37、8 | 8＋1／8×4＋5 | 不一致／一致 | 一致 |
| 37、1／37、3 | 1×37／3×12＋1 | 不一致 | 一致 |
| 513、512 | 512＋1 | 不一致 | 一致 |
| 1024、512 | 512×2 | 一致 | 一致 |

- 1行のblockを含む分け方だけが不一致になった。2行以上のblockだけの分け方は、ARM64でもbit一致した。結果はLinux・Windowsで同じだった。

### x86_64でのk＞512（PR #38の`d6023fa`で判明）

- 試験に加えた「513＝512＋1」は、x86_64のrunner（EPYC 9V74のLinux、EPYC 7763のWindows）で不一致だった。i7-1360Pでは一致した。
- 原因はkcである。
  - gemm-f32のAVX2／FMA kernel（MR＝16、NR＝6）では、`kernel_params`のkcは「64×（L1 associativityを2の累乗に切り上げた値）」になる。これを[512, k]に収める。
  - i7-1360PのP-coreは12-wayなので、kc＝1024≧513となり、kを区切らない。8-wayのCPU（EPYCのrunner、i7-1360PのE-core）ではkc＝512となり、value積（k＝513）を257＋256に区切る。gemv（1行）は区切らない。
- **確認**：同じi7-1360Pで、この試験のprocessを起動時からCPUに固定した（`host_matrix.py`の固定方法）。P-core（CPU 0〜7）では合格し、E-core（CPU 8〜15）では「seq 513, block 512」で不一致になった。
- 1行のblockのbit一致は、archだけでなく、起動したhostのCACHE_INFOにも依存する。k≦512なら、kcの下限512によって区切られないので、x86_64では一致する。
- **最初に差が出る演算**：scores（q·kᵀ）。差はscoresで最大3.6e-7、softmax後で8.9e-8、出力で1.8e-7（いずれも絶対値）。
- value積（probs·v）も、同じprobsから計算して最大1.2e-7の差が出た。2つの行列積がそれぞれ独立に差を生む。

### 既定経路への影響

- forwardの`QUERY_BLOCK`は512である。1行のblockができるのは、seqを512で割った余りが1の入力（513、1025、…、7681 tokens）だけである。
- k＞512の積でkc＜kになるhostでは、x86_64でも、513 tokens以上の該当入力が1 blockの計算とbit一致しない。
- **モデルで、512行ずつのblockと1 blockを比べた結果**（ARM64、4 thread）：

| 入力 | tokens | hidden（1024要素） | 確率 | 判定 |
| --- | ---: | --- | --- | --- |
| synthetic-ocr-ascii-8-512 | 512 | bit一致 | bit一致 | 一致 |
| **synthetic-ocr-ascii-3-513** | 513 | Linux：993要素が不一致（最大9.5e-6）。Windows：972要素（最大5.2e-6） | 3つとも不一致（最大2.5e-7／2.8e-7） | 一致 |
| long-text | 874 | bit一致 | bit一致 | 一致 |
| maximum-candidates | 3206 | bit一致 | bit一致 | 一致 |
| token-limit-8192 | 8192 | bit一致 | bit一致 | 一致 |

- 公開APIは常にblock化して計算する。上の差は「block化前の計算とのbit互換」の差であり、公式refとの数値gateには影響しない。
  - host matrixでは、513 tokensを含む全39件がARM64でgateに合格した。
  - thread数間・process間のbit一致も保たれている。

### 対応

- **#38**：試験`attention_in_query_blocks_is_bitwise_equal_to_one_block`の例外を、1行のblockを含む分け方のうち、次のどちらかに当たるものだけに限った。
  - aarch64の場合。
  - k＞512の積を含む場合（試験では513＝512＋1）。
  - 例外の分け方では、最大絶対差1e-6以下を確かめる（実測は最大1.8e-7）。
  - それ以外は、どのtargetでもbit一致を要求する。従来の試験（seq≦37、block 1／3／8）は、x86_64ではbit一致のままである。
  - 本番のblock大きさの2例（513＝512＋1、1024＝512×2）を試験に加えた。1024はすべてのtargetでbit一致を要求する。
  - 試験コードは`src/backbone.rs`にあるため、runtime build hashが変わる。bundleは再lockが必要である。
- **後続**：最後のblockが1行にならない分け方にすれば（例：…、511、2）、ARM64でも、kc＜kのx86_64でも、bit互換を回復できる見込みが高い。
  - 2行以上のblockは、kcをmに依存せず決めるため、1 blockと同じ区切りで足す。ARM64でも、2行以上のblockだけの分け方はbit一致した。
  - x86_64でkc≧kのhostでは、結果は変わらない見込みである。
  - ただし、既定経路のcodeを変えるため、#38には入れない。採否の判断が必要である（下の「判断が必要な事項」）。

## 2. ARM64のdebug build

### 原因

- `gemm-common` 0.19の`vmulq_f16`・`vaddq_f16`・`vfmaq_f16`・`vfmaq_laneq_f16`は`#[inline]`である。FP16のinline asmを含むのに、`#[target_feature(enable = "fp16")]`がない。
- opt-level 0では、これらが単独の関数として出力される。その結果、assemblerが`instruction requires: fullfp16`で止まる。
- release buildでは、呼び出し元にinline展開されて消えるため、通る。
- **上流**：
  - [gemm#31](https://github.com/sarah-quinones/gemm/issues/31)（2025-08、Open、作者は「known issue」）。
  - [gemm#46](https://github.com/sarah-quinones/gemm/issues/46)（原因は同じ。修正PR #47はdraft）。
  - #39と#43も未merge。gemm 0.19.0より新しい版はない。
- crates.ioのCandle 0.11.0もgemm 0.19を使う。そのため、crateの利用者にも同じ問題がある。

### 試した回避策（ARM64、両runner）

| 方法 | 結果 |
| --- | --- |
| 既定（`cargo build --lib`） | 失敗（fullfp16） |
| `profile.dev.package.gemm-f16.opt-level` ＝1／2／3 | すべて成功 |
| 上の設定で`cargo test --all-features --no-fail-fast` | 試験16件が合格、1件が不合格（上記attention）。統合試験（contract、process、native_process、process_launch）はすべて合格 |
| 上の設定で`runtime/rust`の`cargo test` | 合格 |

- **採用しなかった方法**：全体に`-C target-feature=+fp16`を付ける方法（#31で使われている回避策）。
  - 実行時のCPU判定がcompile時に固定される。そのため、FP16のないARM64 CPUで動かなくなる恐れがある（#46の指摘）。
  - RUSTFLAGSがruntime build hashに入る点も不適である。

### 対応

- **#38**：`.cargo/config.toml`で、`gemm-f16`だけを`opt-level = 1`にした。
  - この設定は`Cargo.toml`ではないので、runtime build hashは変わらない。
  - release build、数値、crates.ioのpackageにも影響しない。pure-jeffはF32で計算し、F16のkernelを呼ばない。
  - CIでは、試験をdebug buildに戻した。
- **利用者向け**：同じ設定を`README.crate.md`に記載した。
- **上流**：#31・#46は既に報告済みのため、新規の報告はしない。修正版が出たら、この設定を外す。

## 3. 期限の超過

### 計測（8192 tokens、`deadline_trace`）

| host | threads | 期限確認の回数 | 確認間の最長 | 期限3秒での停止 | `timeout_reuse`の停止 |
| --- | ---: | ---: | ---: | ---: | ---: |
| i7-1360P（x86_64） | 1 | 145 | 4.7秒 | 4.3秒 | 4.4秒 |
| i7-1360P（x86_64） | 4 | — | 2.4秒（期限3秒の回） | 4.5秒 | 4.4秒 |
| ubuntu-24.04-arm | 1 | 145 | 9.0秒 | 9.0秒 | 8.96秒 |
| ubuntu-24.04-arm | 4 | 145 | 2.9秒 | 5.7秒 | 5.9秒 |
| windows-11-arm | 1 | 145 | 8.7秒 | 8.6秒 | 8.6秒 |
| windows-11-arm | 4 | 145 | 2.8秒 | 5.6秒 | 5.6秒 |

- 期限は、各layerの前と、full attentionのquery blockの間で確かめる。
- x86_64の`timeout_reuse`は、[host matrix](native-host-matrix-2026-10-19.md)の値である。i7-1360Pはノート機で、計測ごとに揺れる。
- 確認間で最長なのは、linear attention（DeltaNet）のlayer 1つ（attentionとMLPを含む）である。ARM64の1 threadでは約9秒かかる。
- 期限を過ぎた後、最初の確認で止まる。したがって、超過の上限は確認間の最長時間である。8.5〜8.9秒の停止は、これで説明できる。
- loadと準備は期限の外である（`deadline_trace`の計測は、forwardの開始から）。
  - load：x86_64で2.0秒、ARM64で5.1〜5.4秒。
  - 準備：0.01〜0.02秒。

### 契約との照合

- **`Model::decide`（同じprocess内）**：「期限は手順の間で確かめ、実行中の行列演算は中断できない」と、API docと`README.crate.md`に明記されている。今回の超過は、この契約の範囲内である。
- **CLI `jeff decide-process`（子processを期限で停止する、強い期限）**：ARM64でも期限どおりに止まった。

| host | 期限 | 戻るまで | 結果 |
| --- | ---: | ---: | --- |
| ubuntu-24.04-arm | 3000／12000 ms（1 thread）、12000 ms（4 thread） | 3.00／12.04／12.06秒 | `timeout` |
| windows-11-arm | 同上 | 3.02／12.06／12.06秒 | `timeout` |
| i7-1360P | 同上 | 3.05／12.05／12.09秒 | `timeout` |

### 対応

- 契約違反ではないので、#38では変えない。
- 確認の間隔を短くする（DeltaNetの途中、attentionとMLPの間）のは、推論loopの変更である。後続のissueに分ける。

## 4. CACHE_INFO

### 実測値

| host | gemmの値（L1／L2／L3） | OSの報告 | 由来 |
| --- | --- | --- | --- |
| i7-1360P、P-core | 48 KiB／1.25 MiB／18 MiB | 同じ | 起動したcoreのcpuid |
| i7-1360P、E-core | 32 KiB／2 MiB／18 MiB | 同じ | 起動したcoreのcpuid |
| ubuntu-24.04（Xeon 6973P-C） | 24 KiB／1 MiB／480 MiB | L1d 48 KiB／L2 2 MiB／L3 480 MiB | sysfs。gemmは、L1／L2を共有する論理CPUの数（SMTの2）で割る（L3は割らない） |
| windows-2022（EPYC 9V74） | 32 KiB／1 MiB／**0** | — | cpuid（仮想機がL3を報告しない） |
| ubuntu-24.04-arm | 64 KiB／1 MiB／128 MiB | 同じ | sysfs |
| windows-11-arm | 16 KiB／512 KiB／1 MiB | — | **gemmのaarch64既定値**（`CACHE_INFO_DEFAULT`）。`cache_info()`にWindows on ARMの経路がない |

### block大きさとの関係（gemm-common 0.19のsource）

- **kc**（kの区切り、すなわち和の区切り）：L1の大きさとassociativityから決まる（`kernel_params`）。下限は512である。
  - kcが変わると、部分和を足す順序が変わる。i7-1360PのP／E-coreの差（3.55e-6）の第一候補である。ただし、未検証である。
- **OSによる違い**：Linuxではsysfsを読み、L1／L2を共有する論理CPUの数で割る。x86_64のWindowsではcpuidを読み、割らない。そのため、同じCPUでもOSによって値が違いうる。
- **mc**：L2から決まる。小さい行列（m・n≤64）では、`CACHE_INFO[1]/kc`から決まる。
- **nc**：L3から決まる。L3が0の場合（windows-2022）は、別の既定値になる。

### 調査計画（#18の後続、#38ではGEMMの初期化を変えない）

1. 各行列積の実際の`KernelParams`を記録する。
   - 対象はモデルが使う形状（projection、MLP、attentionの2つの積）と、本番の長さ（128〜8192）。
   - 値は、gemm-commonの式をCACHE_INFOの実測値（上の表）に当てはめて求める。
   - 演算子をwrapして、実際の(m, n, k)も記録する。
2. P-core値とE-core値でkc・mc・ncが違う積を特定する。
3. 違う積だけを、両方の値で計算する。その差が、forward全体の3.55e-6の差を説明するかを確かめる。
4. 起動CPUに依存しない固定方法の候補を、bit互換・速度・移植性で比べる。
   - 候補は、CACHE_INFOを明示した値で初期化する方法、gemmへの設定APIの追加（上流）、kcの固定など。
   - CPU0やP-coreへのaffinity固定は、既定の解決策にしない。

## 判断が必要な事項

1. **ARM64でattentionのbit互換を回復するか**：
   - 方法：最後のblockを2行以上にする（seq mod 512＝1の時だけ、末尾を511＋2に分ける）。
   - 影響：seq mod 512＝1の入力（513、1025…tokens）で、ARM64と、kc＜kのx86_64 hostの結果が、1 blockの計算と一致するように変わる見込み。それ以外の入力とhostでは変わらない見込み。
   - #38とは別のPRで、golden・host matrixを再確認する。
2. **期限の確認間隔を短くするか**：DeltaNetのlayer内（またはattentionとMLPの間）に確認を加える。ARM64の1 threadで、最長約9秒の超過を縮める。
3. **CACHE_INFOの固定方式**：上の調査計画の結果を待って決める。
